# Fix: key repeat asks the keyboard whether the key is still down

**Date**: 2026-10-09

A Bear note walked to the bottom of the right Samsung for 5 s even with the [10-07 guard](openfile:///Users/sara/Library/CloudStorage/Dropbox/projects/log/2025/hammerspoon/stepper/changelog/2026-10-07-fix-runaway-hotkey-repeat.md) in place. Root cause, reproduced 5 of 5 times with synthetic keys: ==🔴when the modifier comes up before the key while Hammerspoon's main thread is busy, macOS never delivers the hotkey's release==. The guard's modifier check read stale state during the same stall, so only its 5 s cap stopped the walk. Stepper's per-minute layout save had run 2 s late at that moment.

**Change**: ==🟢each stepper press starts `inputprobe hold`==, which polls the HID system's key state and exits when the keyboard lets go. `bindWithRepeat` in [stepper.lua](openfile:///Users/sara/Library/CloudStorage/Dropbox/projects/log/2025/hammerspoon/stepper/lua/stepper.lua) stops at the first tick after that, whatever happens to the release. The modifier check and the 5 s cap stay as backups. A lost release is reported once the keyboard has really let go, then closed with a synthetic key-up, so the next press isn't swallowed. A release now stops only its own key's repeat. The report adds the modifiers at the press and at the stop, plus how long the main thread stalled around the press ([inputprobe.lua](openfile:///Users/sara/Library/CloudStorage/Dropbox/projects/log/2025/hammerspoon/stepper/lua/inputprobe.lua)); wake and unlock times now survive reloads. ==🔵Cost: one short-lived process per stepper press, alive only while the key is down.==
