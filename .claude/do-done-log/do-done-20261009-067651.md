## Why it happens

I reproduced it with a small helper that presses F20 through the HID layer, the same way a real keyboard does:

| Hammerspoon when the key comes up | Release order | Release delivered? |
|---|---|---|
| busy (2 s) | modifier first, then key | ❌ lost, 5 of 5 |
| busy | key first, then modifier | ✓ |
| busy | no modifier | ✓ |
| idle | modifier first | ✓ (3 of 3, counting 10-07's test) |

**If Hammerspoon's main thread is busy when you let go, and the modifier comes up before the key, macOS never delivers that hotkey's release.** fn+↓ has exactly that shape when fn comes up first. Two more things turned a lost release into a walk:
- **The guard read stale modifiers.** While Hammerspoon is busy, the modifier state it reads doesn't update. In the probe, ctrl still read as held about 2 s after release, so the guard saw fn as "still held" and kept stepping until the 5 s cap.
- **The next press gets eaten.** Afterwards macOS still treats the key as down, so your next press of that combo is swallowed.

At 14:45 Hammerspoon was busy: the per-minute layout save, which reads every window through Accessibility, ran 2 s late (due 14:44:59, logged 14:45:01), right as you pressed. 10-07 fits too: Bear deactivated in the same second fn went down. It isn't the wake theory: today's was 2 hours after the last wake.

**Who's to blame:**
- **macOS** drops the release silently. That's the actual loss.
- **stepper** sets it off. It does slow work on Hammerspoon's only thread (the layout saves, Accessibility calls into Bear and Chrome), and its guard trusted the two signals that fail at exactly that moment: the release and the modifier state.
- **Hammerspoon** sets the stage: one thread runs everything, hotkeys included, and it can't read the keyboard's real key state.
- **Not Hammerspoon's own event taps:** pausing them changed nothing. Nothing points at BetterTouchTool, Hyperkey, Siri or Monologue either. The loss happened every time Hammerspoon was busy and never otherwise.

## The fix (loaded, not committed yet)

- **The repeat now asks the keyboard itself.** Each stepper press starts a tiny watcher (`inputprobe hold`) that asks the keyboard layer whether the key is still down, below every tap and hotkey route. The repeat stops at the first step after you let go, whatever macOS does with the release. The modifier check and the 5 s cap stay as backups.
- **A lost release gets closed.** Stepper reports it, then sends a synthetic key-up so your next press isn't swallowed.
- **Reports say more.** They now include the modifiers at the press and at the stop, plus "main thread stalled 2.0s, until …", and the wake and unlock times survive reloads. I updated the README too.

**Tests with synthetic keys:**
