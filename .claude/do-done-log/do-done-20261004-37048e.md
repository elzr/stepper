## Claude:
Your side panels are back in place and the guard now fixes a hub swap on its own. Nothing is committed.

**What was wrong.** The guard did identify both panels by text serial within 5 seconds of the transition. It then asked Lunar to rotate them, four times in two attempts, and Lunar answered "rotation: 270" and "rotation: 90" each time. WindowServer's log shows no rotation at all after 22:16:15. Lunar rotates through a display object it caches the first time it sees a UUID, and after a hub re-enumeration that object is stale, so the command updates Lunar's own number and moves nothing. The nudge from last night changed the input and proved the actuator dead. The "glitch at both" you saw was macOS applying the saved, swapped arrangement as each panel connected, before the guard ran.

**Why the center LGs never do this.** They have unique numeric EDID serials, so macOS carries their UUID over to whatever slot they land on. The log literally says "Adjusting" for each LG. The Samsungs share one numeric serial, so macOS falls back to "Twins" and keys each UUID by the connection slot. The text serial is logged but never used for identity. The guard already used it correctly. The failure was only in the rotation step.

**The fix.** A small Swift tool now calls Apple's MonitorPanel framework directly, by display ID, with a fresh manager each run. It also places both origins in one CoreGraphics transaction, which matters after a swap because each panel sits where the other belongs. The guard builds the tool with swiftc on first use, so only the source is tracked.

- `features/F010-sync-display-names-in-Lunar/display-arrange.swift` is the new tool, with `rotate`, `place`, and `list` commands.
- `lua/displayguard.lua` drops the Lunar path entirely and uses the tool.
- The F010 README, project README, memory notes, and a new case study at `case-studies/2026-10-04-lunar-rotation-caches-go-stale.md` document all of it.

**Verification.** I restored your panels by hand with the tool at 22:30. Then I flipped the right panel to the wrong angle on purpose at 22:34:01 and let the guard's own screen-change trigger catch it. It reported both panels fixed at 22:34:14, thirteen seconds after the flip, with no window drift afterwards.

**What to expect.** macOS saves the corrected arrangement for whichever UUID pair is live, and that pair is a property of the cabling. So after any future swap, or swap back, the panels will come up wrong for about ten seconds and then snap into place. That is the floor for software. Making macOS itself indifferent would need an EDID emulator dongle giving one panel a different serial.

That feature exists, but it stopped being press-count based in February. What you remember is the original design, and what you tried just now hit the current one.

**What the code does today.** A plain hyper+N press cycles open → raise → minimize, and nothing else. Moving the note to the display under your cursor is a separate path, the summon, and it only fires while **right shift is physically held** together with hyper+N. Pressing it again with right shift returns the window to its original spot and minimizes it. The same split applies to the live slots on X/Q/A/Z. The dispatch is in `lua/bear-hud.lua` around line 921.

**Why you remember it differently.** The first version on 2026-02-07 was exactly your description: one hotkey cycling open → raise → summon to cursor → return. On 2026-02-12 that was refactored into two paths, toggle on the bare hotkey and summon on right shift, and the February 13 change made dismissal a per-window minimize. The README's Bear section documents the current split, but it is easy to miss that the summon needs the extra modifier.

**What the console shows from your attempt.** Between 22:26:25 and 22:26:38 hyper+N fired 14 times, and every press logged either "Raising '_mem NOW'" or "Hiding '_mem NOW'", alternating.
