You guessed right: something in Stepper got stuck. It was the key repeat behind fn+→ (move right). The `End` key-up (fn+→) never reached Hammerspoon, so the repeat kept firing 30 times a second, stepping whichever window had focus to the right until it hit the right Samsung's edge.

**Why it never stopped on its own.** Stepper handed key repeat to Hammerspoon. Hammerspoon runs repeat as a single timer that only stops at the next Hammerspoon hotkey press of any kind, and never checks whether the key is still down. Clicking windows couldn't stop it; any Hammerspoon shortcut would have.

**Timeline.** The layout backups and console pin it to about 14:48:32 through 14:49:17. It ended when you pressed hyper+P (spin), not hyper+F; the console has no hyper+F since 11:28. Spin opened this session, but your first message only arrived at 14:58, which made the timing look later than it was.

**Why the key-up went missing.** I couldn't pin that down; nothing was logging key releases.
- **Ruled out:** releasing fn before the arrow. Apple's keyboard code sends End's key-up the moment fn lifts.
- **Ruled out:** releasing modifiers in a different order. A test showed releases match on the key alone, so changing modifiers mid-hold still releases.
- **Ruled out:** Stepper's own event taps. None of them see key-ups.
- **Left standing:** another app's event tap swallowing it (Hyperkey, rcmd, BetterTouchTool and Raycast all run one), or Hammerspoon being busy at that moment.

**The fix** (`bindWithRepeat` in `lua/stepper.lua`). Stepper now runs its own repeat:
- On every step it checks that the keys you pressed, fn included, are still down, and stops the moment they aren't.
- No hold repeats longer than 5 s.
- If it catches a missing key-up, the console logs `[stepper] lost key-up: … in <app>`. The app name is the evidence we lacked this time.

I reloaded Hammerspoon and ran a regression test through the real code using a spare key. All four cases pass: a normal hold, a lost key-up with fn released (stops within 33 ms), fn released just before the key-up (no false alarm), and the 5 s cap.

**Two small behavior changes.** Letting go of a modifier mid-hold now stops the repeat; before, it kept repeating the original action. Holds longer than 5 s stop repeating.

**Logging.** The lost-key-up line now carries the facts we were missing this time, and nothing extra is printed until a key-up is actually lost:

```
[stepper] lost key-up: end in Bear, repeat stopped after 0.3s (fn released) · 7.5 min after wake · 5.0 min after unlock · secure input off · HID holds: nothing
[stepper] taps that could drop a key-up: BetterTouchTool hid · SiriNCService session · Hyperkey session · Monologue annotated · Siri session | since wake: no change
```

- **Wake and unlock times** test your wake theory directly.
- **"HID holds" is the decisive part.** It asks the keyboard layer itself whether End is still down. "end" means the key-up was never produced, so the fault is below every app. "nothing" means it was produced and then dropped on the way to Hammerspoon.
- **The second line names the suspects for that case:** the only apps with an active event tap that receives key-ups (an *event tap* is how apps like BetterTouchTool intercept keystrokes). It also shows which of those changed since the last wake; I take a snapshot at every wake to compare against.

A small Swift helper collects this; Hammerspoon builds it on first use, like `display-arrange`. I deliberately didn't add a Hammerspoon listener to watch key-ups directly: Hammerspoon 1.1.1 can't make passive ones, so every key release you type would wait on it.
